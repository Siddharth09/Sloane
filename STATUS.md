## What we're building

A voice-cloning platform, live in production, with video cloning intentionally paused as a sold feature (see below).

- **Preset voices:** type text, hear it narrated in one of **10 named, fine-tuned voices** — Vicky, Patrick, Alice, Megan, Katie, Brad, Izzy, Robbo, Michelle, Mark (customer-facing names; internal folder/git identifiers stay neutral, e.g. `art_instructor`, `voice_business` — see `web/src/components/VoicePicker.tsx` for the id→name mapping). Fully working, live.
- **Clone any voice:** upload ~10-20 seconds of anyone's voice, type any text, get it narrated back in that voice (zero-shot cloning). Working, live.
- **Video cloning:** **not sold as a feature right now** (home page still honest). Direction after 2026-09-08 fal tests: **talking head** = Kling Avatar + Lucy voice; **cinematic** = Veo + Veo voice — details/assets in `docs/fal-video-research/`. Pro still lists a reserved 30s/mo allotment with disclaimer until credits + `/api/generate-video` ship. Points users to Kling / Utopai PAI as external options meanwhile.

It runs as:
- A **web app** (Next.js, live at **lucylabs.app**, deployed on Vercel)
- An **iOS app** (Expo/React Native, mirrors the web app's voice features) — **confirmed working on a real device via Expo Go (2026-09-09)**, not yet submitted to the App Store. Real bugs found and fixed from that first real-device pass (play-button replay, missing mic-record on Clone Voice, missing decorative background, video trailers never autoplaying) — see "Mobile / iOS App Store" under What's pending.
- A **GPU inference backend** — Modal (default, scale-to-zero + fast warm requests), RunPod Serverless (legacy, kept running to burn down prepaid credit), or an always-on RunPod Pod (manual, hourly) — switchable at runtime with no redeploy (see "Inference backend: Modal, RunPod Serverless, Pod" below) — that both apps call through Next.js API proxy routes (never called directly by clients)

### Audio generation quality — several real bugs found and fixed
- **Truncation bug**: Chatterbox's alignment-stream safety mechanism occasionally forces early EOS. Fixed with a duration-based retry (`generate_sentence_with_retry`).
- **Word-skipping bug**: added real content verification — transcribe each generation with faster-whisper, compare word overlap against the input text, retry on mismatch.
- **Unnatural flat sentence endings**: real DSP fix using the WORLD vocoder (`pyworld`, `apply_terminal_fall`) — forces F0 to actually slope downward from its peak. Went through two broken attempts before landing correctly (see PROJECT_CONTEXT.md Sec 11 for exactly why the first two didn't work) — applies to every voice automatically.
- **Multi-sentence text sounding rushed/disconnected/emotionless**: root-caused correctly — every sentence was being generated as a fully isolated model call with zero cross-sentence context, then stitched with an identical digital-silence gap. Not a training problem, a pipeline problem (affects every voice equally). Fixed by grouping consecutive sentences into one generation call (`chunk_sentences`, up to ~40 words, smaller for data-limited voices — see below) plus randomized pause-length jitter. A synthesized "breath" sound was also tried at pause points, then **removed** per direct feedback ("very unnatural") — pause jitter and chunking stayed, breath did not.
- **`plan_delivery()`** (new, built during this session via a parallel Mac-based Claude Code session working the same file, reviewed and deployed by this session): a real heuristic layer that reads punctuation/discourse cues in the text (questions, exclamations, ellipses/hesitation, quoted dialogue, list structure, soft vs. energetic language) and translates them into small bounded offsets to Chatterbox's real knobs (exaggeration/cfg_weight/temperature) plus a pause-length multiplier — not a fake emotion classifier. Merge order: default → per-voice baseline → these offsets → explicit client override. Live and tested in production.
- **Michelle (meditation) — data fix + LoRA retrain done (2026-09-09)**: `scripts/03_chunk_by_speech.py` was silently **discarding** long Whisper segments; fixed to split-at-gap; recovered **~318 clips / ~29.7 min** (filelist ~319 lines on pod). **LoRA retrained** on that expanded set on a fresh RTX 4090 pod (`sloane-ft-michelle-robbo`, id `1kq3e5i11wwj6j`); adapters + merged T3 checkpoint under `/workspace/sloane/chatterbox-ft-voice_meditation/chatterbox_output/` (`new_lang_adapter/adapter_model.safetensors`, `t3_finetuned_merged.safetensors`). ### Inference backend: Modal (default), RunPod Serverless (legacy), Pod (manual) — migrated 2026-09-09
**Why this migrated**: RunPod Serverless's real-world cold starts measured **~177s** (see the old note preserved below) and, on a later live-production check, **2-3 minutes** on a plain uncontended request — nowhere near the ~30-90s it was originally sized around, and a genuinely bad user experience ("it took a long time, this won't work well" - direct user feedback). Root cause: loading the model off RunPod's network-attached volume on every cold start is disk-I/O bound; that's a platform/architecture problem, not something more RunPod config tuning fixes. Modal's Volume is a different, faster storage layer built specifically for this.

**Real measured Modal numbers (2026-09-09, this migration's own verification)**: cold start (first request to a fresh container) **~141s** — not dramatically better than RunPod's worst case, so don't oversell it as an instant fix. What's genuinely different: a **warm** container (any request within `scaledown_window=300`s, i.e. 5 minutes, of the last one) answers in **~10-17s total**. In practice this means the *first* generation after a quiet period still takes a couple of minutes, but anyone generating a second clip shortly after — or during any real burst of traffic — gets a fast response. This is a real improvement in typical experience, not a full fix of worst-case latency; Modal's "memory snapshotting" fast-restore feature exists and could close that gap further but is explicitly experimental and unproven for this custom (non-LLM) model — a stretch-goal follow-up, not done here.

- **Switch mechanism**: `settings` table in Postgres, key `inference_backend`, values `"pod"`, `"serverless"`, or `"modal"` — read by `web/src/lib/inferenceBackend.ts`, takes effect immediately on the next request, no redeploy. Toggle from `/admin` (password-gated dashboard) via the "Audio generation backend" buttons, or directly: `UPDATE settings SET value = 'modal' WHERE key = 'inference_backend';`. **Default (when never explicitly set) is now `"modal"`.**
- **Architecture** (`scripts/modal_app.py`, new): a Modal App `lucy-tts` with a GPU class `LucyTTS` (`gpu="L4"`, `scaledown_window=300`, true scale-to-zero - $0 when idle beyond that window) plus two lightweight CPU `@modal.fastapi_endpoint` web functions mirroring RunPod's own submit-then-poll contract almost exactly: `POST .../submit` spawns the GPU function async and returns `{call_id}` immediately (well under Vercel's timeout even on a cold start); `GET .../status?call_id=...` does a non-blocking check and returns RunPod-shaped status strings, so `job-status/route.ts` only needed a small dispatch branch, not a rewrite. Current URLs (stable across redeploys, same app/function names): `https://mehta-siddharth09--lucy-tts-submit.modal.run`, `https://mehta-siddharth09--lucy-tts-status.modal.run` — stored as Vercel prod env vars `MODAL_SUBMIT_URL`/`MODAL_STATUS_URL`.
- **`scripts/lucy_tts_engine.py` is unchanged in behavior** - the only edit is a new `MODEL_ROOT` env var (`LUCY_MODEL_ROOT`, defaults to RunPod's `/workspace/sloane`) that every previously-hardcoded path is now built from, so the exact same file runs on both platforms. Modal sets `LUCY_MODEL_ROOT=/models` (the Volume mount point).
- **Model data**: a Modal Volume `lucy-tts-models` (~6.7GB: base pretrained model + all 10 voices' LoRA adapters + reference clips) plus the `chatterbox-ft-art/src` package - the same code already vendored in this repo at `vendor/chatterbox-finetuning-upstream/src` (confirmed byte-identical to what's actually running on RunPod's volume, modulo CRLF from the Windows checkout - diffed with `--strip-trailing-cr` to confirm). One-time upload via `modal volume put lucy-tts-models <local dir> <remote path>`, one call per top-level directory (`chatterbox-finetuning`, each `chatterbox-ft-<voice>`, `training_data`) - see git history of `scripts/modal_app.py`'s docstring for the exact commands if the Volume ever needs rebuilding from scratch.
- **Real gotchas hit standing this up (all fixed, recorded so they aren't rediscovered)**:
  1. `pyworld` has no prebuilt wheel for Modal's CUDA base image and compiles its C++ extension at install time - needs `build-essential` in `apt_install`, which the base image doesn't have by default.
  2. That same base image's Python was built expecting `clang++` specifically - `build-essential` only provides `g++`/`gcc`, so distutils picked a nonexistent compiler and failed anyway. Fixed by forcing `CXX=g++`/`CC=gcc` via `pip_install(..., env=...)`.
  3. First deploy crashed at runtime with `ModuleNotFoundError: No module named 'perth'` (audio watermarking, pip name `resemble-perth`) - not obvious from a casual `pip list` skim of RunPod's venv. Fixed properly by grepping every top-level `import` actually reached by `vendor/.../src/` + `lucy_tts_engine.py` and diffing against what was already installed - real missing set was `resemble-perth`, `conformer`, `diffusers`, `einops`, `omegaconf`, `pyloudnorm`, `s3tokenizer` (excludes `pykakasi`/`dicta_onnx`/`spacy_pkuseg`/`russian_text_stresser`, which the tokenizer only imports lazily inside `try/except ImportError` for Japanese/Hebrew/Chinese/Russian text - unused by this English-only product).
  4. Windows Git Bash/MSYS silently rewrites a leading `/xxx` command-line argument into a Windows path before it reaches a native `.exe` (`modal volume put ... /chatterbox-finetuning` became a path under `C:/Program Files/Git/...` with no error) - the first upload attempt silently went to the wrong remote path. Fix needs both halves right: `MSYS_NO_PATHCONV=1` so the *remote* path argument is left alone, **and** the local path passed as an explicit `C:/Users/...`-form string (not `/c/Users/...`) since with path-conversion off nothing rewrites that half either.
  5. Modal's CLI prints its own unicode progress/success characters (✓ etc.) that crash on Windows' default `cp1252` console encoding *after* the real work already succeeded - looks like a failure, isn't one. Always run `modal` commands from this machine with `PYTHONUTF8=1 PYTHONIOENCODING=utf-8` set.
- **RunPod Serverless is deliberately left running, untouched, and still selectable from `/admin`** - there's remaining prepaid RunPod credit worth using before it's ever fully retired, and it's a same-day rollback path if Modal ever has an unexpected problem. Don't delete `scripts/09_serverless_handler.py`, the `Dockerfile`, or `web/src/lib/runpod.ts` while this is true. Everything below this line about the Serverless endpoint is historical/reference, kept for whenever RunPod credit runs out and the endpoint is finally retired for good:
  - **Required Vercel env vars for RunPod Serverless to work at all**: `RUNPOD_API_KEY` and `RUNPOD_ENDPOINT_ID` (endpoint `2yykjy1xyuecrj`, name `lucy-audio`).
  - **Also check `workersMax` isn't stuck at 0** on the RunPod endpoint - halts all jobs in `IN_QUEUE` forever if so. Check via the RunPod GraphQL API (`myself { endpoints { workersMax } }`); currently 3.
  - **CRITICAL - the `lucy-audio` Serverless endpoint builds from the GitHub branch `serverless-migration`, NOT `main`.** A plain push to `main` has ZERO effect on this endpoint until `git push origin main:serverless-migration` is also run - the RunPod console has no UI to repoint an endpoint's tracked branch. **Never delete this branch.**
  - The image bakes `lucy_tts_engine.py` in at build time (`Dockerfile`'s `COPY`) - a build takes ~2 minutes; check the endpoint's **Builds** tab before assuming a push is live.
  - Real measured cold-start latency, single uncontended request: ~177s (~149s queue delay + ~28s generation) on one measurement, 2-3 minutes on a later one - see the migration rationale above for why this is no longer the production path.

### Full code audit / cleanup pass (2026-09-09)
Ran a systematic review across web, mobile, and the inference engine before a planned careful user review. Real bugs found and fixed:
- **Mobile web (Expo `--web` build) couldn't reach the API at all** — every fetch to `lucylabs.app` failed with a CORS error from the browser (native iOS/Android never hits this, CORS is browser-only). Root cause was two-layered: (1) missing `Access-Control-Allow-Origin` header, fixed via `web/next.config.ts`; (2) **`https://www.lucylabs.app` is the actual canonical domain** (confirmed via `vercel project ls`) — the bare `lucylabs.app` apex 308-redirects to it, and that redirect response itself has no CORS headers, which fails the browser's CORS check before the real response is ever reached.
