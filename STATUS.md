## What we're building

A voice-cloning platform, live in production, with video cloning intentionally paused as a sold feature (see below).

- **Preset voices:** type text, hear it narrated in one of **9 named, fine-tuned voices** — Vicky, Patrick, Alice, Megan, Katie, Brad, Izzy, Robbo, Mark (customer-facing names; internal folder/git identifiers stay neutral, e.g. `art_instructor`, `voice_business` — see `web/src/components/VoicePicker.tsx` for the id→name mapping). Michelle (`voice_meditation`) was removed 2026-09-10, see below. Fully working, live.
- **Clone any voice:** upload ~10-20 seconds of anyone's voice, type any text, get it narrated back in that voice (zero-shot cloning). Working, live.
- **Video cloning:** **not sold as a feature right now, but no longer framed as a vague "coming soon" either** (2026-09-10: home page copy rewritten to confidently describe 3 real, tested modes instead of hedging). **Talking head** = Kling Avatar + any Lucy voice (or Kling's own); **cinematic** = Veo + Veo voice or a dubbed Lucy voice; **ads** (new) = Seedance reference-to-video + a persistent, exclusive-per-account AI actor generated from a text prompt/photo/video, modeled on Arcads.ai — details/assets/real API test results in `docs/fal-video-research/README.md`. Video plan still lists a reserved credits/mo allotment with disclaimer until credits + `/api/generate-video` ship.

It runs as:
- A **web app** (Next.js, live at **lucylabs.app**, deployed on Vercel)
- An **iOS app** (Expo/React Native, mirrors the web app's voice features) — **confirmed working on a real device via Expo Go (2026-09-09)**, not yet submitted to the App Store. Real bugs found and fixed from that first real-device pass (play-button replay, missing mic-record on Clone Voice, missing decorative background, video trailers never autoplaying) — see "Mobile / iOS App Store" under What's pending.
- A **GPU inference backend** — Modal (default, scale-to-zero + fast warm requests), RunPod Serverless (legacy, kept running to burn down prepaid credit), or an always-on RunPod Pod (manual, hourly) — switchable at runtime with no redeploy (see "Inference backend: Modal, RunPod Serverless, Pod" below) — that both apps call through Next.js API proxy routes (never called directly by clients)

### Audio generation quality — several real bugs found and fixed
- **Truncation bug**: Chatterbox's alignment-stream safety mechanism occasionally forces early EOS. Fixed with a duration-based retry (`generate_sentence_with_retry`).
- **Word-skipping bug**: added real content verification — transcribe each generation with faster-whisper, compare word overlap against the input text, retry on mismatch.
- **Unnatural flat sentence endings**: real DSP fix using the WORLD vocoder (`pyworld`, `apply_terminal_fall`) — forces F0 to actually slope downward from its peak. Went through two broken attempts before landing correctly (see PROJECT_CONTEXT.md Sec 11 for exactly why the first two didn't work) — applies to every voice automatically.
- **Multi-sentence text sounding rushed/disconnected/emotionless**: root-caused correctly — every sentence was being generated as a fully isolated model call with zero cross-sentence context, then stitched with an identical digital-silence gap. Not a training problem, a pipeline problem (affects every voice equally). Fixed by grouping consecutive sentences into one generation call (`chunk_sentences`, up to ~40 words, smaller for data-limited voices — see below) plus randomized pause-length jitter. A synthesized "breath" sound was also tried at pause points, then **removed** per direct feedback ("very unnatural") — pause jitter and chunking stayed, breath did not.
- **`plan_delivery()`** (new, built during this session via a parallel Mac-based Claude Code session working the same file, reviewed and deployed by this session): a real heuristic layer that reads punctuation/discourse cues in the text (questions, exclamations, ellipses/hesitation, quoted dialogue, list structure, soft vs. energetic language) and translates them into small bounded offsets to Chatterbox's real knobs (exaggeration/cfg_weight/temperature) plus a pause-length multiplier — not a fake emotion classifier. Merge order: default → per-voice baseline → these offsets → explicit client override. Live and tested in production.
- **Michelle (meditation) — data fix + LoRA retrain done (2026-09-09)**: `scripts/03_chunk_by_speech.py` was silently **discarding** long Whisper segments; fixed to split-at-gap; recovered **~318 clips / ~29.7 min** (filelist ~319 lines on pod). **LoRA retrained** on that expanded set on a fresh RTX 4090 pod (`sloane-ft-michelle-robbo`, id `1kq3e5i11wwj6j`); adapters + merged T3 checkpoint under `/workspace/sloane/chatterbox-ft-voice_meditation/chatterbox_output/` (`new_lang_adapter/adapter_model.safetensors`, `t3_finetuned_merged.safetensors`). Training wall ~72s. **Still live:** `MAX_CHUNK_WORDS_BY_VOICE=14` bandage until ear-tests confirm long chunks are stable; then raise toward ~40 and optionally soften terminal F0 fall for meditation.
- **Robbo (sales) — data expand + LoRA retrain done (2026-09-09)**: was ~16 clips / 9MB; new ~58 min dual-speaker source blended on purpose (not isolated). Ran `/workspace/process_robbo.py` → **~665 clips / ~53.1 min** (`voice_sales` filelist 666 lines). **LoRA retrained** same pod/session; outputs under `/workspace/sloane/chatterbox-ft-voice_sales/chatterbox_output/` (adapter + `t3_finetuned_merged.safetensors`); wall ~149s. Pitch-jitter stopgap still in code — dial down/remove after ear-test. Training pod **stopped** after DONE marker `/workspace/finetune_michelle_robbo.DONE`.
- Real delivery controls (Expressiveness/Speed sliders) remain honestly labeled, wired through both web and mobile. **Default values were off-center on the actual slider tracks** (`expressiveness: 0.6` on a `[0.3, 1.0]` range - true midpoint is 0.65; `speed: 1.0` on `[0.7, 1.3]` was already exactly centered) - fixed in `DeliverySliders.tsx` on both platforms, spotted from a mobile screenshot 2026-09-09.
- **Vicky (art_instructor) — near-silent-output bug found and fixed (2026-09-09)**: a full 10-voice health sweep (prompted by the Modal migration work) found Vicky reproducibly generating 0.14-0.26s clips instead of several seconds, on all 4 retry attempts, every time, regardless of text. Root-caused via direct GPU testing (not guesswork): Chatterbox's alignment-stream safety net was firing on "token_repetition" within the first ~5-100 sampling steps - an almost-immediate collapse, not the longer-chunk instability Michelle/Robbo had. Fixed by swapping her default reference from `00266.wav` to the confirmed-reliable `00010.wav` in `PRESET_VOICES` - a one-line config change, verified working across 3 separate test sentences directly and once more through the real production Modal path (4.16s output). **Two other voices (Patrick/music_instructor, Brad/voice_tech) showed a single suspect near-silent result during the same sweep, but 3/3 immediate retests each came back healthy (7-10s)** - normal stochastic retry-exhaustion noise, not a real bug, don't chase this further unless it reproduces.

### Voice quality + Modal latency fixes, 2026-09-10 (deployed, partially verified - see honest caveats below)

Reported live in one batch: Alice inserting a spurious "so", Megan/Katie/Brad/Mark all skipping words (Katie: "a whole sentence in the middle"), Izzy/Alice/Robbo sounding sped up ("Izzy's default is very fast"), Robbo switching accents mid-sentence, Michelle "not good at all, remove her", and separately "Modal is slow even after warmed up, over 30 seconds." All of the below is in `scripts/lucy_tts_engine.py`/`modal_app.py`, deployed to Modal (`modal deploy scripts/modal_app.py`) the same day.

- **Real Modal latency bug found and fixed - this is the actual explanation for "slow even after warmed up," not just more retries.** `modal app logs` caught a *warm* container (already serving traffic) printing `"loading fine-tuned T3 for 'voice_business' (cache miss)..."` on a real request - i.e. the container-level warm/cold split the docs already tracked isn't the whole story: there's a second, per-voice warm/cold split underneath it. Each preset voice's LoRA adapter loads from the Modal Volume on that *voice's* first request per container, and the LRU cache that avoids reloading it was capped at `MAX_CACHED_VOICES=6` - below the roster size, so a container that had already served 6 different voices would evict and reload on a 7th. Fixed two ways: (1) `MAX_CACHED_VOICES` is now `len(PRESET_VOICES)` (9, comfortably fits L40S's 48GB - was tuned for a 24GB card originally), and (2) `modal_app.py`'s `@modal.enter()` now calls a new `warm_all_preset_voices()` to eagerly preload every voice at container start instead of lazily per-voice. Trade-off stated plainly: cold start gets somewhat longer (adds preloading 9 adapters); every request after that, cold or warm, never pays a per-voice tax again. **Verified**: redeployed, force-stopped old containers, confirmed `"[modal] all preset voices preloaded"` in logs on fresh containers with no crash/OOM. **Not yet verified**: exact new cold-start number, and whether this fully explains every "slow" report the user saw (the pre-existing retry-driven variance documented above is still real and still adds time on top of this).
- **Clone-voice ("record yourself") was completely broken for real recordings, not just slow - fixed and deployed same day.** Browser `MediaRecorder` produces WebM/Opus and the mobile app's `expo-audio` recorder produces M4A/AAC; neither is a WAV container, but the bytes were written straight to a `.wav`-suffixed temp file and handed to `soundfile` (libsndfile), which only decodes WAV/AIFF/FLAC/OGG-Vorbis. Only a real uploaded `.wav` file ever worked - every actual mic recording failed live with `Error opening '/tmp/....wav': Format not recognised.` (reported live 2026-09-10 with a screenshot). Fixed with an ffmpeg transcode step (`_write_reference_wav` in `lucy_tts_engine.py` - ffmpeg was already in the Modal image for an unrelated reason) whenever the bytes aren't already RIFF/WAVE, covering both web and mobile's recording formats. **Verified end-to-end**: synthesized a real non-WAV (AAC/M4A) test file, submitted it through the live Modal clone-voice endpoint, got a completed audio result back.
- **Michelle (`voice_meditation`) removed from the preset roster entirely**, per direct feedback ("not good at all we can remove her") - also the one voice this project's own notes already flagged as never actually fixed (see the entry above: her cap stayed at 14 words because raising it reproduced a near-silent-clip bug even after a 4.5x larger retrain). Removed from `PRESET_VOICES`, `GEN_PARAMS_BY_VOICE`, `MAX_CHUNK_WORDS_BY_VOICE`, and both `VoicePicker.tsx` (web) and the inline voice list in `mobile/App.tsx`. Her LoRA/training data is untouched on the Modal Volume/RunPod network volume - just no longer offered. Billing copy ("All 10 preset voices") and STATUS.md's voice count updated to 9. **Verified**: a real request for `voice_meditation` against the live Modal endpoint now returns a clean `"unknown voice_id, expected one of [...9 ids...]"` error instead of generating her bad audio.
- **Word-skipping (Megan/Katie/Brad/Mark) - retry validation tightened, not yet re-verified against a real repeat of the bug.** `generate_sentence_with_retry` already transcribes every generation with Whisper and retries below `MIN_WORD_OVERLAP_RATIO` (words the input has that the output doesn't) - but multi-sentence chunking (grouping several sentences into one generation call for cross-sentence prosody) means dropping one *entire* sentence out of several can still clear a lenient bar (e.g. losing a 12-word middle sentence out of a 40-word chunk only drops overlap to ~70%, exactly the old 0.7 threshold). Raised to **0.85**. Honest trade-off: this means more retries (more GPU seconds) on borderline generations, which cuts against the separate "Modal is slow" complaint - the real fix for the underlying instability is more training data, not a stricter proxy metric, but this is the honest lever available without retraining. **Not independently re-verified** - would need many repeated real generations to catch the same stochastic bad take again; shipped on the strength of the code-level reasoning, not a reproduced-then-fixed test like the other items here.
- **Alice's spurious "so" - new retry check added, not yet re-verified.** The existing overlap check only measures *missing* input words, so a single hallucinated/inserted filler word barely moves it (one extra "so" among 20 real words is still ~95% overlap either way) - there was no existing signal that would ever catch this. Added `has_spurious_leading_filler()`: if Whisper's transcription starts with a filler word ("so"/"um"/"uh"/"well"/etc.) that the actual input text didn't start with, treat it as a bad take and retry - same stochastic-retry approach already proven for missing/mangled words, not an attempt to surgically edit the audio (no reliable word-level timestamps available to cut cleanly). Only catches a *leading* filler, since that's what was reported; a filler inserted mid-sentence would need a different (harder, less precise) detection approach if it turns out to happen too.
- **Robbo (`voice_sales`) re-tuned for accent stability - a hypothesis-driven config change, not an ear-verified fix.** His `GEN_PARAMS_BY_VOICE` entry (tuned earlier for "sales energy") had `cfg_weight=0.35` and `temperature=0.85`, both *looser* than every other voice's baseline - exactly the two knobs that let a generation drift from the reference accent/pacing and add sampling randomness. Reported live 2026-09-10 as switching accents mid-sentence and sounding sped up - both point the same direction. Pulled `cfg_weight` to 0.55 and `temperature` to 0.65 (tighter than the shared default, prioritizing staying on-accent over sales punch), kept some `exaggeration` (0.55) for energy. **This needs real listening to confirm** - it's a principled correction based on which knobs were pushed and in which direction when the symptom appeared, not a verified-by-ear fix like Vicky's reference-clip swap was.
- **Izzy/Alice/Robbo speed normalization - a starting correction, not ear-verified.** New `SPEED_BY_VOICE` dict applies each voice a baseline time-stretch multiplier (Izzy 0.82, Alice 0.88, Robbo 0.88) that's *multiplied* with whatever speed the client requests (`DeliverySliders` defaults to 1.0, meaning "this voice's own normal pace") rather than replacing it - so the Speed slider still works relative to the corrected baseline instead of silently overriding the fix the moment a user touches it. Chatterbox has no training-time speed knob (confirmed earlier in this project) so this reuses the same real post-generation time-stretch (`apply_speed`) already used for the user-facing slider.
- **Terminal-fall (downward inflection) regression found and fixed same day, verified with real before/after data - not a guess.** After the first round of fixes above, the user reported a demo clip's sentence ending rose instead of falling - the exact thing `apply_terminal_fall()` (see its own docstring history) already exists to prevent. Root-caused by re-running the function's actual pyworld analysis against the real failing clip (`chatterbox_compare.wav`, Megan/`voice_finance`): the natural take had already fallen correctly and fully (356Hz peak -> a genuine low ~77Hz creaky-voice ending, confirmed to be real vocal fry and not a pitch-tracking glitch by re-running the analysis on the full utterance, not just the isolated tail - same result either way), but the old code unconditionally overwrote the whole tail with a forced curve capped at `TERMINAL_FALL_SEMITONES=5` below the peak, which computes out to ~267Hz - **higher** than the already-good natural ending, actively undoing a correct fall and replacing it with a shallower, relatively-higher one. Fixed by taking `min(natural_semitone, forced_target_semitone)` per frame instead of unconditionally overwriting - verified by recomputing both old and new curves against the real extracted pitch data before redeploying (old last-frame target: 266.8Hz; new: 76.6Hz, matching the natural fall). Redeployed to Modal.
- **All 9 remaining preset voices regenerated with this fix and their actual preview-sample sentences, sent directly to the user for a real listen** (Vicky, Patrick, Alice, Megan, Katie, Brad, Izzy, Robbo, Mark) - durations all landed in a consistent 0.25-0.40s/word range with no truncation/silence red flags, but duration alone doesn't confirm quality - **this is real audio for a real ear-check, not a claim that everything now sounds right.** These same 9 files are also the actual assets needed for the voice-preview-sample feature (see below) - save them to `web/public/voice-samples/<voice_id>.wav` once approved rather than regenerating.
- **What's honestly still needed**: everything in this section except the Modal cache-miss fix, the record-format fix, Michelle's removal, and the terminal-fall fix (which has real verified before/after data) was shipped from code-level reasoning plus one non-crashing smoke test per change - **not confirmed by actually listening**. The 9 fresh samples above are a real opportunity to close that gap - the person who reported these bugs should listen to each and say what's better/worse/unchanged before any of the speed/accent/filler-retry changes are called "fixed" rather than "attempted."

### Inference backend: Modal (default), RunPod Serverless (legacy), Pod (manual) — migrated 2026-09-09
**Why this migrated**: RunPod Serverless's real-world cold starts measured **~177s** (see the old note preserved below) and, on a later live-production check, **2-3 minutes** on a plain uncontended request — nowhere near the ~30-90s it was originally sized around, and a genuinely bad user experience ("it took a long time, this won't work well" - direct user feedback). Root cause: loading the model off RunPod's network-attached volume on every cold start is disk-I/O bound; that's a platform/architecture problem, not something more RunPod config tuning fixes. Modal's Volume is a different, faster storage layer built specifically for this.

**Real measured Modal numbers (2026-09-09/10)**: cold start (first request to a fresh container) **~85-141s** — not dramatically better than RunPod's worst case, so don't oversell it as an instant fix. A **warm** container (any request within `scaledown_window=300`s, i.e. 5 minutes, of the last one) is meaningfully faster but **not a fixed ~10-17s** - real back-to-back tests on 2026-09-10 measured 26s and 41s for warm requests, because Chatterbox's own retry-on-bad-generation mechanism (`generate_sentence_with_retry`, up to 4 full attempts) means "warm" total time is genuinely variable, not a constant.

**Root cause of "slow in general" (not just cold start), found and fixed 2026-09-10**: `LucyTTS`'s GPU was `gpu="L4"` - a weaker, cheaper card than the RTX 4090 RunPod was using. Measured sampling throughput directly from `modal app logs`' progress bars: **~13-15 tokens/sec on L4** vs. **~25-29 tokens/sec** seen testing directly on a RunPod RTX 4090 pod during the Vicky investigation - roughly half the speed, on every single generation, warm or cold. **Switched to `gpu="L40S"` (same Ada Lovelace generation as that 4090, $1.95/hr vs L4's $0.80/hr) - measured ~21 tokens/sec after switching, closing most of the gap.** Per-request cost doesn't scale up 2.4x with the hourly-rate difference since it finishes proportionally faster. This is now live.

**Pre-warm-on-page-open trick - tried 2026-09-10, tested working but rejected on UX grounds, reverted**: added a `warmup()` Modal method plus a `/api/warm-inference` route called from `page.tsx`/`App.tsx` the moment the generation page loads, well before the user finishes typing and hits Generate for real. **Real finding: Modal's autoscaler starts a brand-new container for a request that arrives shortly after a warm-up ping rather than waiting for the in-progress one to finish** - confirmed via `modal container list` showing two distinct container ids/start-times for a single simulated user's warmup-then-generate sequence, seconds apart. The only way found to make the two calls actually share one container was `max_containers=1`, which works (confirmed: a later real generate request landed on the already-loaded container, sampling started immediately with no reload delay) but means **every concurrent real user queues behind whoever's already generating** - rejected by direct user feedback ("i dont like the modal plan of users queuing for one gpu it will not be a good result") and reverted the same day. The pre-warm code itself (`warmModal()`, `/api/warm-inference`, `warmup()` on `LucyTTS`) is left in place - harmless to keep firing, just don't rely on it and don't re-add `max_containers=1`.

**Why there's no clean fix for this**: Modal has no concept of "this later request came from the same visitor as that earlier warm-up ping, route it to the same container" - it's stateless, and deciding whether to scale out is a per-request judgment made instantly, not something that waits to see if an in-flight cold start will finish soon (correctly so, for its actual job of handling real concurrent bursts by scaling out). That means on any true scale-to-zero platform, only three options genuinely exist, not four: pay $0 idle and accept the real cold-start hit; pay to keep something continuously warm (Modal `min_containers=1` or a RunPod Pod); or force single-container queuing, which breaks concurrent-user experience. There is no version of "free, fast, and handles concurrent users well" simultaneously - discussed and accepted as a real trade-off, not a bug to keep chasing.

**Memory snapshotting - tried 2026-09-10, made things worse, reverted same day**: enabled `enable_memory_snapshot=True` + `@modal.enter(snap=True)` specifically to attack the cold-start number (this doesn't touch the GPU-speed issue above - snapshotting only affects the loading/init phase, not per-token generation speed once running). Real result: cold start went from ~85-141s to **194s**, and - more damning - the restored container's actual generation speed collapsed to **~3 tokens/sec** (visible directly in `modal app logs`), meaning the GPU/CUDA context did not restore cleanly from the snapshot and left the container in a degraded state for the rest of its life, not just a one-time slow restore. Reverted immediately; confirmed a clean redeploy restores normal ~13-15 tokens/sec and ~85-141s cold start. **Do not re-enable this without a real fix for the post-restore GPU degradation** - Modal's own docs already flagged this feature as unproven for non-LLM-serving custom models, and this is exactly the kind of failure they meant.

**Useful commands for anyone debugging Modal timing directly** (all need `PYTHONUTF8=1 PYTHONIOENCODING=utf-8` set first on Windows, see gotcha #5 below):
- `modal app logs lucy-tts` - tails live logs including the actual per-token sampling progress bars (`Sampling: N/1000 [...it/s]`) - the single best signal for whether a slowdown is cold-start (nothing printing yet) vs. generation-speed (bars printing slower than ~13-15it/s) vs. a real error.
- `modal container list` - shows currently-warm containers for the app.
- `modal container stop <id> --yes` - force-kills a specific warm container (the `--yes` is required non-interactively, or it silently no-ops asking `[y/N]` with no TTY to answer it) - needed to force a genuinely fresh cold-start test rather than accidentally hitting a leftover warm (or in the snapshot experiment's case, degraded) container from a previous test.
