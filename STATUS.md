### Second round of voice fixes, same day (2026-09-10) - real ear feedback on the first round drove all of these

### Inference backend: Modal (default), RunPod Serverless (legacy), Pod (manual) — migrated 2026-09-09
**Why this migrated**: RunPod Serverless's real-world cold starts measured **~177s** (see the old note preserved below) and, on a later live-production check, **2-3 minutes** on a plain uncontended request — nowhere near the ~30-90s it was originally sized around, and a genuinely bad user experience ("it took a long time, this won't work well" - direct user feedback). Root cause: loading the model off RunPod's network-attached volume on every cold start is disk-I/O bound; that's a platform/architecture problem, not something more RunPod config tuning fixes. Modal's Volume is a different, faster storage layer built specifically for this.

**Real measured Modal numbers (2026-09-09/10)**: cold start (first request to a fresh container) **~85-141s** — not dramatically better than RunPod's worst case, so don't oversell it as an instant fix. A **warm** container (any request within `scaledown_window=300`s, i.e. 5 minutes, of the last one) is meaningfully faster but **not a fixed ~10-17s** - real back-to-back tests on 2026-09-10 measured 26s and 41s for warm requests, because Chatterbox's own retry-on-bad-generation mechanism (`generate_sentence_with_retry`, up to 4 full attempts) means "warm" total time is genuinely variable, not a constant.

**Root cause of "slow in general" (not just cold start), found and fixed 2026-09-10**: `LucyTTS`'s GPU was `gpu="L4"` - a weaker, cheaper card than the RTX 4090 RunPod was using. Measured sampling throughput directly from `modal app logs`' progress bars: **~13-15 tokens/sec on L4** vs. **~25-29 tokens/sec** seen testing directly on a RunPod RTX 4090 pod during the Vicky investigation - roughly half the speed, on every single generation, warm or cold. **Switched to `gpu="L40S"` (same Ada Lovelace generation as that 4090, $1.95/hr vs L4's $0.80/hr) - measured ~21 tokens/sec after switching, closing most of the gap.** Per-request cost doesn't scale up 2.4x with the hourly-rate difference since it finishes proportionally faster. This is now live.

**Pre-warm-on-page-open trick - tried 2026-09-10, tested working but rejected on UX grounds, reverted**: added a `warmup()` Modal method plus a `/api/warm-inference` route called from `page.tsx`/`App.tsx` the moment the generation page loads, well before the user finishes typing and hits Generate for real. **Real finding: Modal's autoscaler starts a brand-new container for a request that arrives shortly after a warm-up ping rather than waiting for the in-progress one to finish** - confirmed via `modal container list` showing two distinct container ids/start-times for a single simulated user's warmup-then-generate sequence, seconds apart. The only way found to make the two calls actually share one container was `max_containers=1`, which works (confirmed: a later real generate request landed on the already-loaded container, sampling started immediately with no reload delay) but means **every concurrent real user queues behind whoever's already generating** - rejected by direct user feedback ("i dont like the modal plan of users queuing for one gpu it will not be a good result") and reverted the same day. The pre-warm code itself (`warmModal()`, `/api/warm-inference`, `warmup()` on `LucyTTS`) is left in place - harmless to keep firing, just don't rely on it and don't re-add `max_containers=1`.

**Why there's no clean fix for this**: Modal has no concept of "this later request came from the same visitor as that earlier warm-up ping, route it to the same container" - it's stateless, and deciding whether to scale out is a per-request judgment made instantly, not something that waits to see if an in-flight cold start will finish soon (correctly so, for its actual job of handling real concurrent bursts by scaling out). That means on any true scale-to-zero platform, only three options genuinely exist, not four: pay $0 idle and accept the real cold-start hit; pay to keep something continuously warm (Modal `min_containers=1` or a RunPod Pod); or force single-container queuing, which breaks concurrent-user experience. There is no version of "free, fast, and handles concurrent users well" simultaneously - discussed and accepted as a real trade-off, not a bug to keep chasing.

**Memory snapshotting - tried 2026-09-10, made things worse, reverted same day**: enabled `enable_memory_snapshot=True` + `@modal.enter(snap=True)` specifically to attack the cold-start number (this doesn't touch the GPU-speed issue above - snapshotting only affects the loading/init phase, not per-token generation speed once running). Real result: cold start went from ~85-141s to **194s**, and - more damning - the restored container's actual generation speed collapsed to **~3 tokens/sec** (visible directly in `modal app logs`), meaning the GPU/CUDA context did not restore cleanly from the snapshot and left the container in a degraded state for the rest of its life, not just a one-time slow restore. Reverted immediately; confirmed a clean redeploy restores normal ~13-15 tokens/sec and ~85-141s cold start. **Do not re-enable this without a real fix for the post-restore GPU degradation** - Modal's own docs already flagged this feature as unproven for non-LLM-serving custom models, and this is exactly the kind of failure they meant.

**Useful commands for anyone debugging Modal timing directly** (all need `PYTHONUTF8=1 PYTHONIOENCODING=utf-8` set first on Windows, see gotcha #5 below):
- `modal app logs lucy-tts` - tails live logs including the actual per-token sampling progress bars (`Sampling: N/1000 [...it/s]`) - the single best signal for whether a slowdown is cold-start (nothing printing yet) vs. generation-speed (bars printing slower than ~13-15it/s) vs. a real error.
- `modal container list` - shows currently-warm containers for the app.
- `modal container stop <id> --yes` - force-kills a specific warm container (the `--yes` is required non-interactively, or it silently no-ops asking `[y/N]` with no TTY to answer it) - needed to force a genuinely fresh cold-start test rather than accidentally hitting a leftover warm (or in the snapshot experiment's case, degraded) container from a previous test.

**Conclusions on each video model, as of 2026-09-11 - real, tested findings, the honest state to build future decisions on:**
- **Kling** (`kling-video/ai-avatar/v2/standard` for lip-sync; `v2.1/master` for text/image-to-video; `v1.6/standard/elements` for multi-image): **the reliable one for identity preservation.** Avatar mode animates an exact reference photo to match provided audio rather than regenerating the scene - confirmed twice to preserve identity perfectly (Beth test, then all 5 character-picker preview clips). Real tradeoff: it cannot relocate a character to a new setting - the background is locked to whatever the reference photo shows. `v2.1/master`'s text-to-video duration is a strict `5`/`10` enum (no 8s). `v1.6/standard/elements` (up to 4 reference images) avoided Seedance's content-policy block on our AI-generated faces, but didn't reliably preserve identity or product-logo text either - not a solved path for product-in-hand ads.
- **Veo** (`veo3.1/fast`): the most visually realistic of the three for a single generated scene, and the right choice for the pay-as-you-go "any prompt" flow and the ads-demo video (both single-shot, no persistent-character requirement across multiple generations). **Not reliable for preserving a specific character's identity across a new generation** - real testing (3/3 in one batch, even with minimal-motion "stand still and talk" prompts) showed it regenerating a completely different-looking person from the reference image. This is why it was removed entirely from the character picker's voice options. Duration is a strict `4s`/`6s`/`8s` enum (verified directly against the API schema, not just docs, which were incomplete). No multi-image reference support at all (single `image_url` only).
- **Seedance** (`bytedance/seedance-2.0/fast/*`): flexible duration (4-15s) and the only engine with genuine multi-reference-image support (`reference-to-video`, up to 9 images via `@Image1`/`@Image2`/etc.) - the one capability neither Kling nor Veo has. But its safety filter reads our AI-generated photorealistic character faces as "a real person's likeness" and hard-blocks (`partner_validation_failed`) - confirmed blocking the exact product-ad flow that needed this multi-image capability most. Whether this is fal's own added validation layer or ByteDance's actual model classifier is an open question - emailed fal support (`support@fal.ai`) to ask directly, no reply yet.
- **Sora 2**: **not viable to build on right now.** Available via fal, but the endpoint is already marked "deprecated, no longer supported" as of this check, with public reporting of a full shutdown around 2026-09-24 (~2 weeks out at time of writing). Its `character_ids` feature (reference a named character across generations) is conceptually exactly what this project needs, but building on a model already being wound down would be wasted effort - revisit only if OpenAI ships a real, supported successor API.
- **The real, unresolved gap this points to**: no engine currently offers both "guaranteed same character" and "place them in a new setting via text prompt" at once. Kling Avatar gives the first, gives up the second. Veo/Seedance can attempt the second but don't reliably deliver the first. If "same character, new settings" becomes a hard product requirement, it likely needs either a different technique entirely (a dedicated face-swap/identity-lock model, not currently used anywhere in this stack) or accepting real per-generation identity risk and disclosing it, the way Veo's own-voice option was disclosed before being removed.
